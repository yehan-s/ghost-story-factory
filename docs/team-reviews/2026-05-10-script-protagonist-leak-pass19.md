# 评审团报告: G-273 主角身份泄漏清扫 Pass 19

日期: 2026-05-10
任务: `TASK_SCRIPT_PROTAGONIST_LEAK_PASS19`
Issue: 待创建
决议: 修改后放行

---

## 1. Chief Editor

结论:修改后放行。

主角身份泄漏是正式剧本的硬伤。读者可以接受主角被夜班系统篡改,但不能接受作者自己忘了主角是谁。必须区分“怪谈让身份动摇”和“旧稿设定残留”。

本轮不需要重写赵某,只需要把旧履历残留从正式体验里清掉,并让审计以后能抓到 variant。

---

## 2. State Architect

结论:修改后放行。

这不是新增状态系统的问题。正确做法是收紧文本契约:主角身份约束是一组禁止词和检查入口,属于审计红线,不是运行时 flag。

注意:不要把 `year_violations` 这种 lore 年份检查扩大成阻断,否则会误伤杭州民俗时间线。

---

## 3. Meta-Game Designer

结论:修改后放行。

周目反馈的核心是“我这一轮扮演的是谁”。如果 G-273 主角忽然有妻儿、14 年工龄、1985 入职,玩家就无法理解自己到底是在玩赵某、前任、林某,还是旧稿拼贴。

本轮清扫后,后续多角色周目才能成立。

---

## 4. UX Designer

结论:修改后放行。

TUI 地图首开文案是玩家主动按 `m` 后看到的第一层私人物品反馈。这里写“媳妇合照”会立刻把角色带偏。应该改成“单位备勤机 / 临时工路线图 / 欠费提醒 / 工牌编号异常”这类能支撑赵某设定的细节。

---

## 5. Lore Keeper

结论:修改后放行。

杭州历史年份、旧论坛、民俗档案可以保留。要删的是绑定到“你”的旧中年身份,尤其是妻儿、父母、1985 入职、51 岁、14 年夜班。

G-273 的可怕之处应来自编号把别人压到他身上,不是文本直接把他写成别人。

---

## 6. Topology Designer

结论:放行。

本轮不改拓扑,不改 choice target,风险主要在 JSON 修改和审计误报。改完必须 merge fragments,不能只改正式树。

---

## 7. QA / Path Tester

结论:修改后放行。

必须新增测试证明:

- variant 文本里的旧履历会被 `audit_script_depth` 抓到;
- 正式树不再包含旧履历泄漏;
- TUI 首开地图文案不再出现“媳妇”等旧主角字段。

---

## 8. 风险清单

- 误删 lore 风险:合法历史年份和民俗背景不能被清掉;
- 误改主角风险:赵某不能变成空白人,仍要保留缺钱、临时工、工牌压力;
- 审计风险:只扫默认 narrative 会再次漏掉 variant;
- TUI 风险:硬编码文案不进 tree,容易逃过剧本审计。

---

## 9. 执行建议

1. 先补 Task / Issue / milestone;
2. 清理 fragment 中已定位的旧履历 variant;
3. 修 TUI 地图首开硬编码;
4. 扩展审计和测试;
5. 合并 fragments 并跑完整验证。
